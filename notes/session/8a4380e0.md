**In QEMU's codebase, `target/` means "target CPU architecture" (the architecture being emulated), not build output.**

Each subdirectory is a different architecture QEMU can emulate:
- `target/arm/` = ARM emulation code  
- `target/i386/` = x86 emulation code
- `target/riscv/` = RISC-V emulation code
- etc.

The **build outputs** go in `build/` (which mirrors the source structure).

So `target/arm/hvf/hvf.c` is the **ARM-specific HVF acceleration code** (source), while `build/target/arm/hvf/` contains the compiled objects.

The split is:
- **`accel/hvf/`** - shared HVF infrastructure (host-side, architecture-agnostic)
- **`target/arm/hvf/`** - ARM-specific HVF code (handles ARM registers, exceptions, VCPU state)
- **`target/i386/hvf/`** - x86-specific HVF code

It's architecture-specific because even though HVF is a macOS host feature, the code must translate between QEMU's ARM CPU state and HVF's ARM virtualization APIs - completely different from how it works for x86.
